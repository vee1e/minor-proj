The stopwatch was measuring the wrong thing

Every result this project produced sat on one table of numbers — which solver won on which puzzle. That table was wrong, for a reason nobody could see. Here is what happened, in plain language, and what it takes to get to a finished project.

What you're building

The premise, before any of the bugs

You have seven different programs that all solve the same kind of logic puzzle. None of them is best at everything. Some are quick on one shape of puzzle and hopeless on another.

The idea: train a model that glances at a new puzzle and says "use solver #4 for this one." If it works you get most of the speed of always having chosen the best tool — without needing to know in advance which one that is. This is a real, well-studied problem; the gap between "best single solver" and "always picked the right one" is large and has stayed large for twenty years.

To train that model you need a training table. Take thousands of puzzles, run all seven solvers on each, write down who won. That table is the foundation. Everything else in the project sits on top of it — the models, the charts, the statistics, the report.

Keep this in mind

If the table is wrong, nothing built on top of it can be right, and none of the later machinery will complain. A model trained on bad labels doesn't crash. It produces a confident, professional-looking answer that happens to be meaningless.

Four things went wrong. Each one was invisible on its own, and together they produced a result that looked like a finding.

What went wrong

The diagnosis, one bug at a time

Bug 1 · the root cause

The stopwatch started too early

Imagine timing runners in a race, but you start the clock while they're still tying their shoelaces and walking to the start line. If the race itself only lasts three seconds, the shoelace-tying is most of what you measured — and you end up crowning whoever ties shoes fastest.

Before a solver can work on a puzzle, the code has to hand the puzzle over to it, clause by clause. That handover takes time, and it's different for each of the seven solvers.

The timer was started before the handover. So the recorded "runtime" was handover + solving. On easy puzzles that finish in milliseconds, the handover is most of it.

MiniSat is the oldest and simplest of the seven, so it has the lightest handover. It "won" almost every puzzle. The table of winners was really a table of which solver has the least setup overhead.

Bug 2 · the amplifier

The good examples were thrown in the bin

A sensible rule, badly calibrated: "if it's too close to call, don't count it." Except the definition of "too close" was wider than every race being run.

There was a reasonable-sounding rule in the code: if two solvers finish within a hair of each other, don't pretend one is "the right answer" — mark it a tie and leave it out of training. Fine in principle. It stops the model learning from coin flips.

But "a hair" was defined as 50 milliseconds, and on this corpus every puzzle was finishing faster than that. So every puzzle was a tie. Every puzzle was discarded. The model was left with almost nothing.

And here's the part that made it invisible: a model with nothing to learn from doesn't error out. It quietly falls back to answering the most common label every single time. That is your "always MiniSat".

Bug 3 · the setting

The puzzles were too easy to have an opinion about

Like ranking race cars by having them drive to the end of the driveway. Everyone arrives at once.

The generated puzzles were small and far from the difficulty peak. Every solver finished every one of them almost instantly. There was genuinely no difference to detect — and critically, no amount of extra data fixes that. You need harder puzzles, not more easy ones.

This is why "the sample size is too small" was the wrong diagnosis. A bigger sample of puzzles nobody struggles with tells you nothing, with great statistical confidence.

Bug 4 · why it survived

Nothing ever said what the model was answering

The system reported a score. It never once reported "by the way, I'm saying MiniSat 100% of the time."

This is the one I'd underline, because it's the reason the other three survived so long. A single line of output — a count of which solver got picked — would have made the collapse obvious on day one. Instead the pipeline produced a plausible number and everyone reasonably assumed it meant something.

That count now appears in three places: the dataset summary, the results file, and the report. There's also a new satsel diagnose command that prints it plainly, without retraining anything and without needing a dashboard.

So who was right?

Your teammates were right that the output was garbage. The explanation — "sample size" — was wrong. More data on the old pipeline would have produced the same broken answer with tighter error bars, which is arguably worse: a wrong result that looks more rigorous.

Two more, found along the way

Neither was on the original list

The code couldn't read real benchmark files

SATLIB is the standard public collection of these puzzles — the set essentially everyone in this field tests against. Two things stopped you using it:

  • The download code pointed at a website that has been a dead, parked domain for years. Every download failed quietly into a debug log, and the puzzle generators filled the gap. The corpus looked complete.
  • Even when I pointed it at the live archive, every file was rejected — because real SATLIB files end with a % character, and the parser crashed on it. Every genuine benchmark instance was being discarded as corrupt.

Both fixed. A test run now pulls 59 real instances out of 117, including the unsatisfiable sets — puzzles with no solution at all. Those matter more than they sound: to prove no solution exists, a solver has to exhaust every possibility, so there's no lucky early exit to flatter a weak one. That's exactly where the seven solvers differ most.

The neural network was ignoring the word "not"

In these puzzles a clue can be "x is true" or "x is not true". The old graph code stripped the sign off every clue before feeding it to the network. So two completely different puzzles looked identical to the model.

Where you are right now

The honest status board

The machine is built and every part of it works. It has simply never been run at full size. That's the whole remaining gap.

One distinction worth being precise about

"The dataset is missing" is easy to misread, so to be exact: the puzzles are not missing. They are a free download that takes minutes, and 2,210 real SATLIB instances are wired up and working — more than the 2,000 the synopsis asks for.

What's missing is the answer key: how long each of your seven solvers takes on each puzzle, on your hardware. That cannot be downloaded, because it doesn't exist anywhere — it is the output of running your experiment. You can download the racetrack; you can't download your own lap times.

Nor can you borrow someone else's. PAR-2 comparisons are only meaningful inside one consistent measurement environment — same machine, same solver builds, same timeout. Mixing published numbers from different hardware would break the fixed profiling protocol your synopsis makes a selling point of.

Nothing so far proves the hypothesis. What's been proven is narrower: the old "always MiniSat" result was a measurement artefact, not a finding about the world. That clears the way for a real test — it isn't the test.

Two things do support the premise: once timing was fixed the winners spread across five different solvers on their own, and across just nine test puzzles the best-possible chooser picked four different solvers. So per-puzzle differences are real and measurable. Whether a model can exploit them is the open question.

Getting to the full thing

Five steps, in order

1

Rehearse on your own laptop

~1 hour · resumable · do not skip

Run the pilot, then check three numbers: are puzzles taking longer than 50 ms, do at least 30% show a real speed gap, and are there more than 100 usable training rows?

uv run satsel all --small --no-gnn --workers 8
uv run satsel diagnose
2

Stop at the gate

a decision, not a command

If those numbers fail, the puzzles are still too easy — fix the generators before booking anything. This one hour protects an entire lab session. It is also the exact check that would have caught the original bug on day one.

Resist the temptation to loosen the thresholds to make more training rows appear. That is precisely how the first version produced a confident, meaningless answer.

3

The big run

several hours · lab machine · this is the missing piece

Seven solvers × three repeats × ~2,000 puzzles. This is the expensive part and the thing that doesn't exist yet.

It needs CPU cores and a quiet machine — not the GPU. Solver search is branch-heavy and sequential; there is nothing in it for a graphics card to parallelise. Use about half the physical cores, because workers running flat out interfere with each other and distort the very timings you're recording.

4

Train and read the result honestly

minutes

A genuine result needs all four: the selector beats the best single solver, the confidence interval excludes zero, it survives the multiple-comparison correction, and it picks at least three different solvers.

That last one isn't a formality. A "selector" that always picks one solver isn't a selector — it is that solver, wearing a hat.

5

Close the remaining gaps, then write it up

optional but promised in the synopsis

Three things the write-up currently claims that the code doesn't do. None of them blocks anything — they are write-up polish, not obstacles:

  • SATfeatPy isn't on PyPI, only GitHub. Our extractor already computes 63 features across the same categories. Vendor the repo, or reword to "a SATfeatPy-derived feature set" — both defensible; the second avoids depending on unmaintained research code days before a deadline.
  • The feature-free baseline is close to free, because the GNN is already feature-free: it learns from raw graph structure, not hand-crafted vectors. What's missing is running it as an explicit no-node-features ablation and labelling it as the comparison point.
  • The probe overhead is real work, about half a day: 0.46 s per puzzle of Python process startup, which breaks the 5% extraction budget you promise.

Then write it up including what didn't work. A negative result you can defend is worth more than a positive one you can't.

The foundation was measuring the wrong thing, so everything built on it was meaningless. That's fixed. What's left is to actually run it — and that's a CPU job, not a GPU one.
