From here to a dataset worth reporting

The pipeline bugs are fixed and merged into the PR. What remains is producing data. Work through these in order — step 3 is a real gate, and going to the lab before passing it will waste the session.

1

Verify the environment

any machine

Do this on your machine now, and again on the lab machine before anything else. It installs nothing in --check mode and exits non-zero if something is wrong.

python scripts/bootstrap.py --check --gnn

A healthy result names Python 3.11, confirms all core packages import, and reports the torch build. On the lab machine you want to see CUDA YES. If you see CPU-only wheel, fix it before training:

python scripts/bootstrap.py --gnn --cuda
Known trap

On Windows, pip install torch from PyPI installs a CPU-only build with no error at all. Training then runs on the CPU and simply looks slow. A CUDA build that is too old for the GPU is worse — it installs cleanly and fails only at runtime with “no kernel image is available for execution on the device.” The --check pass compares the GPU's compute capability against the kernels the installed torch actually carries, so it catches both.

2

Run the pilot here first

your machine · 30–60 min

This is the cheap rehearsal. It profiles ~560 formulas and tells you whether the corpus actually separates solvers — the thing that was broken. Do not skip it: every failure it can catch is one that would otherwise surface at the lab.

uv run satsel all --small --no-gnn --workers 8
uv run satsel diagnose

It is resumable. Every completed formula is checkpointed into artifacts/runs/profiling.db, so Ctrl-C and re-running the same command continues rather than restarting.

Then read the three numbers that decide everything, in artifacts/datasets/dataset_summary.json:

FieldWhat it meansYou need
median_best_time_sHow long the fastest solver takes on a typical formula> 0.05
informative_rateFraction of formulas with a real runtime spread across the portfolio> 0.3
n_train_usableTraining rows that survive the informative filter> 100
real_instance_shareFraction from SATLIB rather than the generators> 0.25

satsel diagnose prints all of these plus the label distribution and any warnings, so you usually do not need to open the JSON.

3

Go / no-go

decision

Book the lab if

  • GO median best time is above 50 ms and informative rate is above 0.3
  • GO the label distribution names three or more different solvers
  • GO warnings is empty or only mentions small test-set size

Fix first if

  • WAIT a family's median best time is still under 50 ms — check family_median_best_time_s. Colouring and scheduling are the likely culprits; scale those two generators up again in bench/generators.py.
  • STOP informative_rate is near zero, or n_train_usable is 0. The corpus still cannot separate solvers, and more data will not change that. Nothing trained on it means anything.
The whole point

The original bug was not a small sample — it was a corpus and a measurement that could not tell solvers apart, plus a model stage that never said so. These thresholds are the guard against repeating it at 20× the scale.

4

At the lab: what the hardware is for

lab machine
Read this before planning the session

The GPU is almost irrelevant to this project. Solver profiling is the bottleneck and it is pure single-threaded CPU work — CDCL search is branch-heavy pointer chasing with no data-parallel structure to exploit. It cannot be GPU-accelerated. The GNN is a small model on a few thousand graphs: minutes on a CPU, and perhaps 1% of the project's total compute.

What you actually need from that machine is core count and a quiet system. If the Blackwell box is paired with a large Threadripper or Xeon, take it — for the CPU.

StageUsesRough cost at N ≈ 2,000
ProfilingCPU only~100+ CPU-hours; 4–14 h wall clock depending on workers
Feature extractionCPU onlyminutes
Classical trainingCPU only1–3 min
GNN trainingGPU helpsminutes either way
Measurement fidelity

Your entire dataset is timing measurements, so a busy or thermally throttling machine produces garbage labels. Parallel workers also contend with each other for memory bandwidth and cache, which inflates and adds noise to the very runtimes you are recording — this is why SAT competitions limit per-node parallelism. Use about half the physical cores, on an otherwise idle machine, and let the median-of-3 absorb the rest.

5

Full profiling run

lab machine · hours

Set the worker count to roughly half the physical cores. On a 32-core box:

uv run satsel bench                      # downloads SATLIB + generates the rest
uv run satsel features --workers 16
uv run satsel profile --workers 16 --heartbeat 30

The profiler prints a heartbeat with rate and ETA, processes easy families first so progress is visible immediately, and checkpoints every formula. If it dies, re-run the identical command and it resumes.

Confirm the corpus before committing hours to it:

uv run satsel bench
python -c "import pandas as pd; d=pd.read_parquet('artifacts/manifests/formulas.parquet'); print(d['source'].value_counts())"

You should see a healthy satlib count. If it is zero, the machine has no network route to cs.ubc.ca — the run will still work, but the corpus will be entirely synthetic and provenance_warnings will say so. Copy artifacts/raw/_cache/ from a machine that does have access instead.

6

Training

lab machine · minutes
uv run satsel build
uv run satsel train                      # RF / XGBoost / SVM / regret + SATzilla baseline
uv run satsel train-gnn --epochs 40      # GraSS tripartite GNN

The GNN picks its device automatically. To pin it explicitly — worth doing if profiling is still running and you want the GPU left alone, or vice versa:

SATSEL_DEVICE=cuda uv run satsel train-gnn --epochs 40    # force GPU
SATSEL_DEVICE=cpu  uv run satsel train-gnn --epochs 40    # force CPU

On Windows PowerShell use $env:SATSEL_DEVICE="cuda" instead.

Training writes a per-layer ablation (1 / 2 / 4 layers), the histogram of solvers it chose on validation, and a warning if it collapsed onto one solver. Check artifacts/models/model_diagnostics.json for the classical side — the collapsed flag is the one to look at.

Honest framing

A selector that beats the best single solver but picks only one solver is not a selector — it is that solver. The choice histogram is what distinguishes a result from an artefact, which is why it now appears in the report and diagnose.

8

If it still collapses

diagnosis

Work down this list; the order is by likelihood.

  1. Corpus too easy. Check family_median_best_time_s. Any family under 50 ms contributes noise, not signal — scale that generator up or drop the family from training.
  2. One solver genuinely dominates. Check unique_share in portfolio.json. If one solver is strictly best on 70%+ of instances, a constant predictor is a strong baseline and that is a legitimate finding — report it as one rather than forcing a win.
  3. Features carry no signal. Check the feature ablation table: if syntactic-only matches all-features, the graph and probe features are not helping, and the GNN is the better bet.
  4. Not enough usable rows. n_train_usable under ~200 makes every model unstable. More instances is the only fix.
Do not do this

Do not lower label_min_spread or widen the tie margin to manufacture training rows. That is how the original bug produced a confident, meaningless selector. If the corpus cannot separate solvers, the honest report says so.

Still open in the code

Known gaps against the synopsis, none of which block the run above:

  • The feature-free upper bound (Zhang et al. 2026) that O6 compares against is not implemented.
  • SATfeatPy is not used — features are hand-rolled, 63 of them, against the stated “SATfeatPy, d ≤ 120”.
  • Feature-probe overhead is ~0.46 s per instance of Python subprocess start-up, which breaks the 5% τfeat budget on easy instances.
  • Repeat runs are not seed-varied — pysat rejects the seed kwarg, so the three runs capture timing noise only. Fine for median labels; say so in the methodology.
  • Kissat crashes in-process on some pysat builds. It is profiled in an isolated subprocess and pruned as dominated.
  • The corpus is roughly half generated. Reported honestly, but raise the SATLIB share if C1 is to claim a benchmark collection outright.
